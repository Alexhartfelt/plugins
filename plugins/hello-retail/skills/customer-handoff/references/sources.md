# Sources — which tool or file fills which field

Read alongside `handoff-template.md`. Every value in the document carries one of the **source
tags** below. When a source is unavailable, write the exact wording in *Unavailable-source
wording* — never a guess and never a blank.

## Source tags (fixed set)

| Tag | Meaning |
|---|---|
| `MCP` | hello-retail MCP tool result (name the tool when it helps: `MCP search_listConfigs`) |
| `detected` | read from the storefront itself via the Playwright MCP (platform, theme, SPA, language) |
| `card` | ClickUp task fields — status, list, assignees, dates, custom fields, description |
| `comment <author> <dd/mm>` | a ClickUp comment; author and date always |
| `time-in-status` | `clickup_get_task_time_in_status` history |
| `QA <file>` | a report, brief or coverage file under `QA/<customer>/` |
| `session` | the skill run that just finished (its hand-off message, retro, MISSING DATA) |
| `operator` | the operator's answer in the Step 3 interview |
| `computed` | derived from other sourced values by the definitions below |

## Platform vocabulary (§1, mandatory)

Use exactly one of these, then a middle dot and the flavour (`Shopify · Dawn 15.2`) for theme / frontend and version when visible.
Detection: the snippet in `../../tile-extractor/SKILL.md` → *PLATFORM DETECTION* (scripts, meta
generator, globals, markup) run in the Playwright MCP; the per-platform notes live in
`${CLAUDE_PLUGIN_ROOT}/docs/wiki/platforms/<platform>/`.

| Value | Typical flavours | Typical signature |
|---|---|---|
| `Shopify` | theme name + version (Dawn, Horizon, Impulse, Prestige…) | `cdn.shopify.com`, `Shopify.theme` |
| `Magento 2` | `Luma`, `Breeze`, `Hyvä <version>` | `mage/`, `requirejs`, `hyva` globals |
| `WooCommerce` | theme (Flatsome, Storefront, Astra…) + WooCommerce version | `woocommerce` body class, `wp-content` |
| `Shopware` | `5` / `6`, theme | `shopware` globals, `/widgets/` |
| `BigCommerce` | Stencil theme | `cdn11.bigcommerce.com` |
| `DanDomain` | classic / Webshop 8 | `generator = DanDomain` |
| `Lightspeed` | eCom (C-Series) | `webshopapp.com` assets |
| `Starweb` | — | `starweb` assets |
| `Viskan Streamline` | — | `viskan` assets |
| `Wikinggruppen` | — | `wikinggruppen` assets |
| `PrestaShop` | version, theme | `prestashop` globals |
| `Centra` | — | `centra` API calls |
| `Custom` | framework (Next.js, Nuxt, headless X) — say which | none of the above |

Two candidates or no match → carry both / `Custom (unidentified)` to the Step 3 interview.
Never infer the platform from the domain, the TLD or a similar customer.

## Where the documents live — `output/handoffs/` for now

**Phase 1: local.** The documents are written under the operator's working directory in
`output/handoffs/` — `output/` is gitignored and is where the other skills already put per-customer
artefacts. The layout and the front matter are the **ingestion contract** for whatever comes next
(a shared repository, a vector database): keep both exactly, and moving the store later is a copy.

Keyed on identity that never changes (company → website). Platform is an attribute in the front
matter, never a folder — customers replatform, and one company can run two platforms.

```text
output/handoffs/                             ← HR_HANDOFF_ROOT overrides this (e.g. a shared checkout)
  INDEX.md                                   generated by scripts/build-index.sh — never edited by hand
  companies/
    <companyId>-<company-slug>/              e.g. 12345-example-group
      README.md                              company level — see company-readme-template.md
      <websiteUuid>-<domain>/                e.g. 0f3c1a2b-…-example-shop.com
        handoff.md                           the document (handoff-template.md)
        cases/                               optional — long scripts linked from §5
```

Root resolution: `$HR_HANDOFF_ROOT` when set → otherwise `output/handoffs/` in the working
directory (create it). When the root is a git checkout, `git pull --ff-only` before reading and
propose a commit after writing — the operator commits. Slugs: lowercase, kebab-case, ASCII; the
domain is the registrable domain.

**Sharing until the store is shared:** the run ends by reminding the operator to attach
`handoff.md` to the ClickUp card; Step 1 looks for that attachment when the local file is missing,
so a second developer on another machine continues the same document.

## Stage plan (§2, front matter `stages`)

Built once, on the first run, then only appended to. Fixed vocabulary — these nine names and no
others, so the index can compare stages across customers:

| Stage | Always? | Added when the card sells… | Handed off when |
|---|---|---|---|
| `setup-data` | **always** | — | product feed(s) created (and order feed / tracking noted); `feed-setup` / `feed-migration` finished |
| `search` | | Search | `search-developer` pushed the REVIEW draft and `search-qa` ran at least once |
| `recommendations` | | Recommendations | `recom-developer` REVIEW draft + `recom-qa` |
| `pages` | | Pages | `pages-developer` draft + `pages-qa` |
| `retail-media` | | Retail Media | banner slots / campaign config in place |
| `newsletter` | | Newsletter Content | `newsletter-developer` design saved + `newsletter-qa` |
| `triggered-emails` | | Triggered Emails | base + ordered flows delivered + `newsletter-qa` lane T |
| `product-agent` | | Product Agent / Klaviyo | channel connected and settings confirmed |
| `launch` | **always** | — | the close mode: every other stage done or skipped, card Done, §3-C written |

Rules:

- **Source of the plan:** the card's sold-feature list → cross-checked against the MCP (an existing
  config / box / feed puts that feature in scope even when the card is silent) → confirmed by the
  operator on the first run. Card and MCP disagree → ask; never pick silently.
- **Scope grows:** an upsell adds a row with `ordered` date and who ordered it (comment author + date).
- **Scope shrinks:** never delete a row — set `skipped (<reason>, <date>)`; sold-vs-delivered still
  accounts for it.
- **A Search-only customer has three stages** (`setup-data`, `search`, `launch`); a full-suite customer
  has up to nine. The header line's `Stage n/m` uses the plan's row count as `m`.
- **QA is not a stage.** The QA skills run per feature; their runs and fix rounds are columns on the
  feature's own ledger row.
- **Status values:** `planned`, `in progress`, `done`, `skipped (reason, date)`.

## Two modes

| Mode | Trigger | Writes |
|---|---|---|
| **record** (default) | "write the handoff", "record this for [customer]", a skill's end-of-task offer | §1, §2 (stage status), §3-A row for the stage just finished, §3-B refresh, §4 for that feature, §5 new cases, §6–§9 as they changed, §10, task-log entry, front matter `updated` and `stages` |
| **close** | "close the onboarding", "final handoff", "hand over to CSM" | refused unless every non-`launch` stage is `done` or `skipped` — then §3-C, `launch` → `done`, front matter `closed` + `final: true`, §2 close date, task-log entry |

A record run that finishes the last feature stage says so and offers close; it never closes on its
own.

## Field map

### §1 Customer

| Field | Source |
|---|---|
| Domain(s), Website UUID, Company ID | `website_getInfo` (domain → uuid → companyId); multi-domain: `website_listForCompany` |
| Platform, theme, SPA, language | `detected` (SPA: client-side routing without full reload; language: `<html lang>` + TLD) |
| Implementation (Script / API) | `MCP search_listConfigs` — `target: NONE` configs and no served design mean API; else Script. Confirm from the card when both appear |
| Integrations | `productAgents_getChannels` (Klaviyo), card description |
| Reference sites / designs | card description + comments (the QA brief's *QA surface* section already extracted them) |

### §2 Project (ClickUp)

Fetch per `../../qa-checklists/SKILL.md` → *Step 1.5*: compact task first (status, `list.name`,
assignees, dates, creator), then `include: ["description"]` alone, then
`include: ["custom_fields"]` **alone and last** — it fails on cards with a large Customer dropdown;
when it does, write the roles from assignees / operator and tag the source accordingly. Card not
in the Onboarding list → confirm with the operator before using it.

| Field | Source, in order of preference |
|---|---|
| Card ID + URL, List, Status | compact task |
| Project owner | custom field named like *Project owner* / *Owner* / *PM* → card creator **only if** the operator confirms → operator |
| Developer(s) | custom field named like *Developer* / *Implementation* → assignees (one assignee = developer; several → ask who held which role) → operator |
| CSM | custom field named like *CSM* / *Customer Success* / *Account manager* → operator |
| Start date | card `start_date` → `time-in-status`: first transition into an active status → card `date_created` → operator. **State which** in the Source column |
| End date | `time-in-status`: transition into Done / Closed → today, when the document is written at hand-off and the operator confirms the onboarding is complete → `ongoing (as of <today>)` |
| Sold features | the card's feature list / checklist names (Search, Recommendations, Pages, Retail Media, Newsletter, Triggered Emails, Product Agent, Feeds) |

No ClickUp MCP → the browser lane in Step 1.5 (Claude in Chrome, read-only) or the operator's
paste; roles and dates then carry `operator`. No card at all (operator confirmed) → §2 rows read
`no card (operator confirmed)` and §3 time-in-status rows read `not available (no card)`.

### §5 Unique cases

Candidates come from four places; every candidate becomes a case or is explicitly dropped in
the interview:

1. Provenance lines in a `*-developer` hand-off (`session`) — each workaround with its root cause
   and removal condition.
2. *Declined* and *Decisions* entries in the QA brief (`QA <file>`) that required a non-standard build.
3. MISSING DATA items that were resolved by a customer-side or manual change.
4. The operator's own list (Step 3, question 1).

### §6–§8

| Section | Source |
|---|---|
| Decisions · Declined · Known open | `QA/<customer>/*-qa-brief-*.md` (already author + date cited); else card comments; else `none` |
| QA summary | every `QA/<customer>/*-qa-*.md`: date from the filename, verdict from the Summary, FAIL count from Issues Found, manual count from *Manual checks for the operator* |
| Open items | *Handoff fix plan* entries not yet applied + *Known open* + MISSING DATA still open; owner from the entry's *Apply via* |

## Performance definitions (§3)

- **Start date / Close date** — as resolved in §2; the Source column names the rule used.
- **Stage started** — the date of the first task-log entry for that stage (a subtask start date on
  the card wins when present). **Stage handed off** — the date of the task-log entry that met the
  stage's hand-off condition (table above).
- **Working days per stage** — Monday–Friday between stage started and handed off, inclusive.
- **Total duration** — start → close: calendar days inclusive of both ends, and working days.
- **Working days** — Monday–Friday, inclusive; no holiday calendar.
- **Days in each status** — from `time-in-status`, one decimal; the current status counts up to today.
- **Days waiting / blocked** — sum of statuses whose name contains *waiting*, *blocked*, *customer*,
  *on hold*, *pending* (case-insensitive). Name the statuses counted. No such status → `0 (no waiting status on this list)`.
- **QA runs** — number of `QA/<customer>/*-qa-<YYYY-MM-DD>.md` reports, split by the feature in the
  filename (`search-qa`, `recom-qa`, `pages-qa`, `newsletter-qa`, `triggered-email-qa`).
- **Fix rounds** — for each feature, the number of QA reports beyond the first (each later report
  is a re-QA after a fix round). Zero reports → `not recorded`.
- **Build rounds** — diff/approval rounds reported by the `*-developer` retro, per design.
- **Open items** — the row count of §8 at the time of the run.
- **Days since start (3-B)** — start → today, calendar and working.
- **Sold vs delivered** — *Sold* from the card's feature list; *Delivered* `yes` when a LIVE config /
  box / design exists, `partial` when only REVIEW / DRAFT exists, `no` when nothing exists;
  `skipped (reason)` when the card sold it and the team consciously did not build it.

## Unavailable-source wording (fixed)

| Situation | Write exactly |
|---|---|
| The value exists nowhere the skill can reach | `not recorded` |
| A tool or connector is missing / errored | `not available (<tool or reason>)` |
| The section legitimately has no content | `none` |
| The operator confirmed there is no ClickUp card | `no card (operator confirmed)` |
| A credential appears on the card | `see ClickUp card` — never the value |
